## SQL Assistant 17.5 — what changed

V17.5 is built **on the V17.4 code, functionality and UI** (`SOURCE_PROVENANCE.md`). Nothing was rebuilt. The V17.4 UI is unchanged except for the minimum that the V17.5 features need: a **Pull Schema** tab on the Schema page, a **Schema passphrase** panel in Settings → Schema Management, and the **CASE / DECODE** controls under a selected column.

### Fixed — table tick-marks (Manual Selectors → Tables)
* **Root cause (reproduced in a real browser first):** the table row's click handler called `preventDefault()`. When the *checkbox itself* was clicked, the browser reverted its native toggle after the handler ran, so the table was added to the query (`2 selected`, SQL updated) but the **tick stayed empty**; removing a table through the checkbox left the **tick showing**. Clicking the row *text* looked fine, which is why it was intermittent.
* **Fix:** the native checkbox is the single source of truth. A click on the box or on the row toggles it natively (the tick is set in the same task as the click) and the `change` event updates the query state. No `preventDefault`, no re-render, no reload. Selected columns, filters, joins, Advanced Options, generated SQL, description, search text and scroll are untouched; the keyboard (Space) works too.

### Added — schema-based CASE / DECODE for columns
* **Columns → select a column → Display as: `Column` | `CASE / DECODE`.** With CASE / DECODE chosen, a second control separates **Manual** from **From Schema**.
* **From Schema** reads the **active schema only**: it lists the column's definition (for example `1 = Open · 2 = Approved · 3 = Rejected`), writes it as **CASE** (every dialect) or **DECODE** (Oracle only; the *Style* control is hidden elsewhere and CASE is used) and applies it to the generated SQL. The definition is **re-read from the schema every time the SQL is built** — it is never copied into the query — so a schema update or pull changes the SQL immediately.
* **No definition → no invention.** The column shows *"No CASE/DECODE definition is available for this column in the active schema."*, the SQL keeps the plain column and the builder adds a warning.
* **Manual is preserved exactly** (the existing manual DECODE builder and Advanced Options → Add Manual CASE). Moving between *Column / From Schema / Manual* never loses a manual expression (it is parked and restored). A column that carries a manual DECODE now stays **ticked** with its settings instead of vanishing from the picker.
* **Everything is persistent:** the choice lives in the central query state, survives tab switches, page refresh (session draft) and schema changes.
* **Describe What You Need / offline NLU:** "status description", "decoded status", "status as text", "… using decode / case" select the schema CASE/DECODE; Oracle + "decode" → DECODE. A decode request for a column without a definition is **reported, not invented**. A column the user already configured — including its CASE/DECODE — is never overwritten or duplicated.
* **Learned queries and the Admin Query Library:** a pattern records *that* a column was shown through a CASE/DECODE matching its schema definition (a free-form manual CASE is not mistaken for one). When reused, the definition is taken from the **current** schema; if the schema no longer defines it the plain column is shown and a note says why.
* **Validation:** schema CASE/DECODE passes all 12 checks in every dialect, also next to an aggregate (the decode of a grouped column is valid). Two latent validator bugs this exposed were fixed: `CAST(x AS VARCHAR(255))` was misread as a column alias named `VARCHAR`; and an expression built only from grouped columns was reported as "not in GROUP BY".

### Added — passphrase-protected cross-device schema synchronization
* **Schema → Pull Schema** (Hamburger menu → Schema → *Pull Schema*; deep link `#schema-used/pull`). Short instructions, a **masked passphrase field with a show/hide (eye) button**, *Remember on this device*, **Pull Schema**.
* **Workflow:** validate the passphrase → retrieve (existing repository connection) → decrypt → validate (format, version, tables, columns, data types, relationships, CASE/DECODE, required metadata) → **compare** (this device ↔ repository: version, updated date, contents, action) → **Apply** or **Cancel** → import → activate → refresh Manual Selectors, Describe What You Need, the offline NLU, SQL generation and CASE/DECODE **without restarting**. Nothing is written locally until *Apply*.
* **Transactional:** the import reuses the existing validated, rolled-back registry write. A wrong passphrase, missing/corrupted/invalid file, decryption failure, network failure, older schema or a cancelled pull **leaves the existing local schema, the active schema and the sync metadata exactly as they were** (tested for each case).
* **Versioned, never blindly overwritten:** every schema carries id, version and updated time; the file carries writer, **application version** and **schema format version** (clear header and inside the ciphertext). An older repository copy never replaces a newer local one ("The synchronized schema is older than the current local schema and was not applied."); changed on both sides is a conflict, not an overwrite.
* **Administrator (Settings → Schema Management → Schema passphrase):** set or change the passphrase, **Save passphrase and publish encrypted schema**, remove it from the device. Changing the passphrase = publish again; other devices type the new one under *Pull Schema* (a device with the old one is told the passphrase is incorrect).
* **Same repository, same architecture:** the encrypted file lives next to the plain registry (`…/schemas/registry.enc.json`), is read and written by the existing `SyncService` (same GitHub client, same publish gate, same 3-way merge rules, same rollback). With a saved passphrase the ordinary **Sync with GitHub Now** and the background sync use the encrypted file; **without** a passphrase synchronization is exactly the V17.4 plain behaviour.
* **Messages** (exact wording): incorrect passphrase, schema unavailable, decryption failure, validation failure, older schema, successful pull, passphrase could not be validated, cancelled. A new operation always starts clean — no stale error survives a success.

### Security (details in `SECURITY.md`)
AES-256-GCM, PBKDF2-SHA-256 (310 000 iterations), random salt and IV per write, header bound to the ciphertext (tampering is detected), separate "check" seal that distinguishes a wrong passphrase from a damaged file. The passphrase is stored on a device only as ciphertext under the non-extractable device key; it is never in the repository, a URL, a log, an error message, the page text or the source. No hard-coded key or passphrase exists.

### Compatibility
No migration needed. V17.4 schemas, learned queries, the Admin Query Library, the Secret Vault, GitHub synchronization, settings and the Admin Password are read as they are. The plain registry file now also carries `appVersion`. Test-only hook `encryptForTest` exists **only** with `?e2e=1` (same mechanism as the existing test hooks).
