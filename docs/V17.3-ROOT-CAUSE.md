# SQL Assistant V17.3 — Root cause analysis

## Issue 1: schema synchronization still failing
The validator and the legacy-migration rules worked on the test data. Sync still failed because the V17.2.1 and V17.2.2
packages read and wrote **different locations** from V17.0–V17.2. These were regressions in those packages:

| # | Defect in V17.2.1/V17.2.2 | Effect | V17.3 fix |
|---|---|---|---|
| A | Local schemas stored under `sqla.schemaRegistry.v15`; V15–V17.2 use `sqla.registry.v15` | After upgrading, the device saw only default schemas. Its real schemas were invisible, and the first publish could overwrite the repository with the defaults | Canonical key restored; data in either key is read, merged by name and moved to the canonical key |
| B | Default repository file `schemas/schema-registry.json`; V17.0–V17.2 use `sql-assistant-data/schemas/registry.json` | The upgraded device synced against an empty or new file. The real legacy file (AP schema 77) was never migrated or rewritten, so V17.2 devices kept reporting the same error | Default path restored. Saved V17.2.1 paths are corrected automatically. If the configured path is empty but a known path has a file, sync stops and names that path instead of creating a second file |
| C | The lossless `code`→`rawValue` rule (L1) ran only for files without a writer stamp | A stamped file passed on by a V17.1/V17.2 device with `rawValue:""` next to `code` was rejected | L1 now applies to every file. The other legacy rules (L2–L6) still apply only to unstamped files |
| D | The writer label `17.2.1`/`17.3` without a third digit | Older readers could not parse it as x.y.z and reported the file as "V17.0 or older" | Writer is `SQL Assistant 17.3.0` |
| E | GitHub reads could come from the HTTP cache; files over 1 MB return no inline content | A stale copy or an empty file could be read | `cache: 'no-store'`; large files are read through the blob API |

## Empty decode values: what they mean and how they are handled
| Case | Meaning | Rule |
|---|---|---|
| `rawValue` is empty but `code`/`value`/`raw`/`key` is not | Export or serialization defect | **L1**: use the first non-empty alias (lossless) |
| Raw value and label both empty | Empty placeholder | **L2**: removed (legacy files only) |
| Label present, raw value missing everywhere | Incomplete export; the code was lost | **L3**: label kept in `unmappedDecodeLabels`, not used in SQL, never invented. It can be restored with *Recover decode codes from source file* or a row edit |
| Empty string or NULL as a meaningful mapping | Not supported by this schema model (NULL uses `IS NULL` filters) | Still a validation error in current-format files |

## Issue 2: index page not working
1. The V17.2.1 project-root `index.html` loaded `/src/main.ts`. Browsers cannot run TypeScript, so the page stayed blank. This is reproduced in the browser test.
2. The V17.2.1 `dist/index.html` used a module script, which browsers block on `file://`.
3. A start-up error before the app mounted was never shown.

V17.3 fixes:
- The build writes the same self-contained app to `dist/index.html`, to the project-root `index.html` and to `release/` (with `404.html` and `.nojekyll`).
- No generated page references `src/` or a module script, and the build fails if one does.
- The shell renders before services start.
- Hash routing makes `/`, any base path, refresh and direct links work.
- Synchronization never runs during start-up.
