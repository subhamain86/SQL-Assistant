# SQL Assistant V17.6.9 — changelog

Baseline: **V17.6.8** (the supplied package; nothing was rebuilt from an older release and no file was replaced wholesale). Seven source files changed; the UI changed in two modules only.

## 1. Admin Password — the default is confirmed, never presumed (`src/services/passwordService.ts`, `src/v17/services/adminPassword.ts`, `src/ui/pages/settings.ts`, `src/main.ts`)
* **Root cause.** V17.6.8 still had a *provisional* default (`default-unverified`, `defaultAllowed: true`) for (a) a device with no repository connection at all ("standalone"), (b) a device whose own repository credential was refused, and a published copy that merely **listed no record** counted as proof that no password existed. A new or different device that had not (yet) reached the central record was therefore *not* distinguished from an uninitialized installation, and `admin` opened Settings even though a non-default central password existed.
* **Fix at the boundary.** States are now `loading | central-applied | local-fallback | confirmed-default | error`. `confirmed-default` is reported only by `AdminPasswordService.resolution()` — an explicit central reset record, a reset held locally, or the **authoritative** repository answering "no record" after the repository was verified. `verifyPassword()` accepts the default only for `state === 'confirmed-default'`. A synchronization in progress on a device without a marker reports `loading`. Published-copy "no record" → `error`. Failed read / refused credential / no connection / invalid record → `error`.
* **Unchanged:** `sqla.pwvault.v15`, `sqla.adminpwmeta.v1765`, the encrypted verifier format and derivation, revisions, repository paths, publish-first ordering with read-back, optimistic concurrency, stale-session re-lock, the unlock ticket, the Secret Vault.
* **Behaviour change (deliberate):** a brand-new standalone device without a repository connection no longer opens Settings with `admin` (it cannot know that no central password exists). Use the navbar **Sync** or *Pull Schema* to connect first. A standalone device cannot *reset to default*. See `docs/ADMIN_PASSWORD.md` → "First-time initialization".
* **UI:** only the lock-screen hint text, the removed "accepted provisionally" toast (`settings.ts`) and the version-history entry (`other.ts`). Layout, theme, cards, typography, spacing, navbar, footer: byte-identical (hash-checked by `test/v1769.test.mjs`).

## 2. Tests, build and pipeline
* **Orphans / stale files.** The CI log's 54 orphaned `.ts` files and 5 historical test files (`engines`, `v1756`, `v1758`, `v1759`, `v176` — 23 failing tests) are **not part of the V17.6.8 package** (it contains none of them; 266/266 pass). They exist only in the target repository, left behind by copying packages over it. V17.6.9 adds a **separate** detector (`npm run check:stale`) and a reviewed list (`scripts/stale-files.json`, reasons per file) with explicit, re-verifying removal commands (`prune-orphans --delete`, `prune-stale --delete`). Nothing is deleted automatically and **no orphaned code was restored into production** (see `docs/STALE_FILES_V17.6.9.md`).
* **Hosted vault.** `src/v17/services/hostedVault.ts` (V17.5.8) is an orphan; V17.6.3 replaced it by the published copy read through `vaultRetrieval.ts` (`via: 'repository-published'`). No stub was added; new tests exercise the production modules and assert that the old modules do not exist.
* **Version tests.** Current-version assertions live in `test/v1769.test.mjs` + `test/support/version.mjs`; historical tests assert shape only or use `test/fixtures/historical-stamps.json`; browser suites read the version from `package.json`.
* **TypeScript.** `scripts/build.mjs` resolves the project-pinned TypeScript (node_modules / `$NODE_PATH`) and refuses any other version; the `/opt/oai-docgen/...` fallback is gone. `npm run check:toolchain`.
* **Production entry point.** `tsconfig.json` (`files: ["src/main.ts"]`, strict unchanged) is unchanged; a test asserts that `build/esm` contains exactly the production graph.
* **Artifact integrity.** `npm run verify:artifact`; `npm run security` now also scans the root page and everything under `release/`.
* **Workflows.** `deploy-pages.yml`: hygiene + artifact steps, failure summary, deploy only on `needs.build.result == 'success'`; `deploy-broker.yml`: the preflight reports every missing key by name (`Deployment blocked: AZURE_CREDENTIALS is not configured.`), no value printed, Azure login not bypassed; no workflow uses `continue-on-error`.
* **PAT diagnostics.** `scripts/verify-pat.mjs` reports HTTP 403 as a failed verification, with upstream code / trace / correlation ids, causes marked unverified, retry guidance; the PAT is never printed.
* **`npm run clean`** keeps `dist/sql-assistant-data/` (the published copy is not build output).
