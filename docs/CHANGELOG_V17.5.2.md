## SQL Assistant 17.5.2 — what changed

V17.5.2 is a targeted stabilization of **V17.5.1** (the attached `SQL-Assistant-V17.5.1.zip` is the baseline — see `SOURCE_PROVENANCE.md`). The UI, architecture, file formats, encryption and deployment workflow are unchanged. Every change below was driven by a **reproduced** defect or a gap found by investigation; each has a Node test and/or a real-browser test.

### A. Manual Selectors → Tables — the tick is painted immediately
* **Root cause (measured, reproduced).** V17.5 removed the `preventDefault()` that reverted the checkbox, but the click handler still did *all* the work synchronously: rebuild the SQL, run the 12-point validation and Explain, then redraw the column list and the filter list. A browser cannot paint the tick until JavaScript returns. On the 77-table AP schema at 4× CPU throttle (a normal office laptop) one click blocked the main thread for **47–113 ms**; the first frame carrying the tick arrived **34–91 ms** after the click (**~260 ms** until the next frame), growing with the number of selected tables.
* **Fix.** The tick, the count and the selection state still change *inside the click itself*. The expensive refresh now runs **once, after the next paint** (`requestAnimationFrame` → `setTimeout`), and several quick clicks share one refresh. Result at the same throttle: handler **0–3 ms**, first frame **1–6 ms**.
* **Consistency.** Selected tables, ticks, the count, the generated SQL and the dependent column / filter lists agree after the refresh (tested with 25 rapid clicks on one table and a burst across all tables: parity-correct, no duplicates). Search, module filter, tabs, schema switching, Select all / Clear, keyboard and refresh behave as before.
* *Intentional behaviour change:* the SQL / validation panels update one frame (≈ 16 ms) after the tick instead of in the same task. One V17.5 test that asserted "SQL in the same task" was changed to wait for it.

### B. Manual and schema-based CASE / DECODE — only valid definitions are offered
* **How definitions are stored (unchanged).** `column.decode = [{ rawValue, label }, …]` (plus `unmappedDecodeLabels` for legacy labels whose code was lost). CASE vs DECODE is a *rendering choice* (DECODE on Oracle only), not something the schema stores — so "a schema with a CASE definition" and "a schema with a DECODE definition" are the same stored data written two ways, and both are tested.
* **New single authority** `v17/engines/decodeDefinition.ts`: **none** (no definition → only Manual), **valid**, **incomplete** (labels without a code) and **invalid** (empty code or label, one code with two labels, not a list). Used by the column picker, the SQL engine, the offline NLU and the notes — so the UI and the SQL can never disagree.
* **Picker.** *From Schema* is offered **only** for a valid definition; otherwise the option is **disabled** ("From Schema (not available)") and the reason is shown ("the active schema has no definition for it" / "is incomplete (2 labels without a code (Blocked, Frozen))" / "is invalid (code "A" has an empty label)"). A valid definition shows `table.column — N values` and the mapping. Manual CASE/DECODE is unchanged and always available.
* **No silent SQL from a damaged definition (was a defect).** V17.5.1 generated `THEN ''` from an empty label and silently dropped unmapped labels. Now no CASE/DECODE is generated, the plain column is used, and the builder / Describe What You Need explain why.
* **Schema switching.** Definitions are read from the active schema every time the SQL is built; switching schemas updates the picker and the SQL at once, and switching back restores them (tested over valid / none / partial / invalid schemas through the real *Schema → Stored Schemas → Set Active* UI).
* **Two defects found and fixed:** (1) two decoded columns with the same name — `STATUS` exists in three built-in tables — produced the **same alias twice** and the SQL failed validation; both now get table-qualified default aliases (a single column keeps `STATUS_DESC`). (2) For a **numeric-coded** column the `ELSE` branch returned the raw number next to text labels, which **PostgreSQL rejects** (*CASE types text and integer cannot be matched*); non-text columns are now converted in PostgreSQL / MySQL / Generic as Oracle and SQL Server already were (text columns and Oracle output are unchanged).

### C. Cross-device schema synchronization — honest, typed, bounded
* **Architecture unchanged** (same repository, same Secret Vault connection, same encrypted `registry.enc.json` / plain `registry.json`, same 3-way merge and rollback). No new backend.
* **A local edit is never reported as synchronized.** New `SyncService.status()` + a status block in *Schema → Pull Schema* and *Settings → Schema Management*: connection, schema passphrase saved?, last download / publish, **schemas with changes not yet published** (until a push really succeeded), unresolved conflicts, and the latest failure. The Manual Schema Update confirmation now says *"Saved on this device (not yet published to the shared repository …)"*. Failed publishes are now logged so they show.
* **Typed repository errors** (`auth` 401 · `permission` 403/429 · `not-found` · `conflict` 409/422 · `timeout` · `network` · `config`), tokens redacted from every message.
* **Request time limit (was a defect).** The GitHub client had **no timeout**: one request that never answered blocked every later synchronization (they are serialized). Every request now has a 20-second limit (`AbortController`); the next sync runs normally. Owner / repository / branch are validated before use.
* **Pull Schema messages name the failure and the next step:** token rejected, no permission / rate limit, timeout, network, missing file, **incompatible format** (newer encrypted or registry format → "update SQL Assistant"), validation failure (with location), decryption failure, wrong or missing passphrase — each states that the local schema was not changed.
* **Conflicts (was a defect).** A preview whose only difference was a conflict said *"already up to date"* and offered no button, so the conflict could never be recorded from the Pull tab. It now shows the conflict, names the schema and offers **Record the conflict for resolution**; nothing is overwritten; the result is a **partial** result, not "success"; *Settings → Schema Management → Use Local / Use Remote* resolves it.
* **No misleading success.** A pull that kept a newer local copy or recorded a conflict now shows *"Schema pull completed only partly."* (warning) instead of *"Schema pulled and validated successfully."*.
* **Multi-schema & idempotence** (tested): schemas are exchanged independently; repeated pulls change nothing and duplicate nothing; an update to one schema never touches another.

### D / E. Schema menu, passphrase and instructions
* *Hamburger menu → Schema → Pull Schema* (existing tab) now shows, without revealing any secret: repository connection, **schema passphrase: saved (encrypted) / not saved / unreadable**, sync state; the **8-step instructions** (menu → Schema → passphrase → pull → authentication → choose → wait → verify), in two compact columns (the original three-sentence help is unchanged); *Open Settings → Secret Vault* when the connection or token is missing.
* The saved schema passphrase is masked by default with a show / hide button (unchanged); *Remove saved passphrase* updates the status.
* **The Vault Sync Passphrase is never stored on any device** (by design, V17.4) — it therefore cannot be displayed. The page says so and where to enter it. Nothing here bypasses the Admin Password: entering or changing the repository connection stays in Settings → Secret Vault.

### F–I. Security, compatibility, errors
No cryptographic or file-format change (plain registry format 2, encrypted `sqla-schema-sync` format 1, vault envelope — all read exactly as before, tested with V17.5.1-style files). No new storage keys. No secret in logs, URLs, repository files or messages (checked in the browser tests against every request body the shared remote received).

### Limitations (see the release summary)
Not tested against **github.com** itself — the build environment has no network access to it and no credentials. The cross-device tests use the app's real GitHub client against an **emulation of the GitHub Contents API**. PostgreSQL / MySQL behaviour of the generated SQL is covered by validation and unit tests, not by running a database. `package-lock.json` does not exist in the project, so a lockfile install was not possible (the only dev dependency is TypeScript).
