# V17.2.1 — Legacy schema migration and synchronization

## Symptom
`1 of 3 schema(s) in the repository failed validation and were not loaded — your local copies were kept unchanged.`
`AP schema 77 … Column "IA_ACTION_LOG.ROOT_DOCUMENT_TYPE" has a decode entry (#1) with an empty raw value … and 434 more.`
`file written by SQL Assistant V17.0 or older (it has no writer stamp)`

## Root cause (confirmed with the actual schema file)
The AP schema (77 tables, 1,561 columns) contains **exactly 437 decode entries** (3 reported + "434 more"),
and **every** entry uses the original export shape `{ "code": "...", "label": "..." }`. Legacy files also use
`primary_key`, `foreign_key: {table, column, validated}` and `schema_name`.
The V17.1/V17.2 reader picked the first *present* alias for the raw value, so an empty `rawValue` beside the
real `code` (as written by V17.0 devices) or a missing mapping produced `rawValue = ""` for all 437 entries.
The validator (correctly) rejected each one, and because the file carried no writer stamp the
repository could never be repaired by a V17.0 device.

## Semantics of an empty decode raw value
| Case | Meaning | Rule |
|---|---|---|
| `rawValue` empty but `code`/`value`/`raw`/`key` present | Legacy representation / export defect | **L1** use the first *non-empty* alias (lossless) |
| raw empty **and** label empty | Empty placeholder row | **L2** remove (reported) |
| raw empty, label present, no alias | Code lost by an older version (incomplete migration) | **L3** keep label in `unmappedDecodeLabels`; not used in SQL; warning; restorable |
| NULL mapping / empty-string mapping | **Not** supported by this schema model (NULL uses `IS NULL` filters) | never inferred |
Other legacy rules: **L4** exact duplicate entries de-duplicated; **L5** `primary_key`/`foreign_key`/`schema_name`
mapped; **L6** foreign keys to tables outside the schema kept as `unresolvedReference` (documentation only).
Anything else (decode not a list, conflicting duplicate codes, empty names, broken relationships) is **not**
repaired: the schema is rejected with an exact path and the local copy is kept.

## Pipeline
```
Repository → Download → Parse → Detect writer stamp
  ├─ current : Validate → Merge → Save → Activate
  ├─ legacy  : Migrate (L1–L6) → Validate → Merge → Save → Activate → Publish (stamped)
  └─ invalid : Reject safely (exact schema/table/column/index/property) → local copy preserved
```
* Validation is never disabled; the same empty raw value in a **stamped** file is still an error.
* Content hashes exclude volatile metadata → re-reading the same legacy file is "unchanged" (no loop).
* Publish protection: `serializeRegistry` refuses any invalid schema and always writes
  `formatVersion: 2, writtenBy: "SQL Assistant 17.2.1", writtenByDevice, writtenAt`.
* Publishing is postponed (with explanation) if it would delete unreadable repository schemas.
